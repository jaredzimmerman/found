# T14: Make build-site.sh survive DreamHost's flaky node launches
Tier: opus · Reviewer: fable · Deps: T08

## Brief
Goal: on the shared DreamHost host, node 18 intermittently aborts at launch (`pthread_create: Resource temporarily unavailable` -> SIGABRT/exit 134, sometimes SIGTRAP 133) or hangs at startup, and `bash: fork: retry` was seen once (T08/T09 reviews, 2026-10-07). Today one such flake in any `node` step turns a whole 6-hourly run into `fatal` and the site stays stale until the next cron slot. Make the build resilient WITHOUT hiding real failures.
Contract: PLAN.md C5, C6, C8; read `.ladder/tasks/T08.md` and `.ladder/tasks/T09.md` (what they saw and what deploy's quick-step retry does; reuse that pattern/helper if it is in `ops/lib.sh`, but build-site.sh must stay self-contained on DreamHost: do not source files outside the deploy unit).
Files: `build-site.sh`, `tests/build-site.test.sh` (new cases), `tests/fixtures/` stubs as needed. No other build/*.mjs changes.
Rules:
- A `run_node` wrapper used for EVERY node invocation in build-site.sh (test-imports, fetch, dc-fetch, validate-feed, record-run, inline `node -e` helpers). Quick steps (everything except fetch/dc-fetch): per-attempt `timeout 60s`, up to 3 attempts, retry ONLY when the failure is a launch flake: exit 134 or 133 or 124 (hang) or 139, or exit 1 with the stderr containing `pthread_create` / `Resource temporarily unavailable` / `fork: retry`. A script/logic failure (any other exit, e.g. validator exit 1 with its normal message, syntax error) is NEVER retried. Backoff 3 s, 8 s. Each retry prints one line `retry node <step> (attempt n/3, reason)` into the run log and increments a counter surfaced in history/status (`node_retries`).
- fetch.mjs and dc-fetch.mjs: retry ONCE, and only if the process died of a launch flake within the first 90 s (before it could have fetched much). A death after 90 s, or any normal exit, is not retried (it would double the load on the sources and mask real breakage). fetch stays under `FETCH_TIMEOUT`; the retry shares that overall budget.
- Reduce the cause too: export `UV_THREADPOOL_SIZE=2` and add `--v8-pool-size=1` / `NODE_OPTIONS` ONLY if you verify on DreamHost (node 18.19.1) that node accepts them and still runs the replay-equivalent workload; document the finding. Do not guess flags.
- `record-run.mjs` must be invoked with the same wrapper; if it still cannot run after 3 attempts, the script appends a minimal hand-written JSON line (printf, no node) to `logs/history.jsonl` and writes `logs/status.json` via a bash fallback so the watchdog never loses a run silently.
- New test cases in `tests/build-site.test.sh` using stub node-launch failures (a stub `node` earlier in PATH that aborts/hangs/exits N the first k times): flake then success => `published` with `node_retries` >= 1; three flakes => fatal at that stage; real validator rejection => NOT retried (one attempt, outcome `rejected`); fetch flake within 90 s retried once; fetch failure after the window not retried; record-run fallback line is valid JSON.
Acceptance: `bash tests/build-site.test.sh` exits 0 on the Mac, and ALSO on DreamHost via `tar c . | ssh hermes 'ssh dh-backup "rm -rf /tmp/t14 && mkdir /tmp/t14 && tar x -C /tmp/t14 && cd /tmp/t14 && bash tests/build-site.test.sh"'` (retry the harness itself once if node flakes before the first test starts; clean /tmp/t14 after); `bash tests/run-all.sh` exits 0; `bash tests/replay/run.sh` exits 0.
Constraints: no password handling; prod untouched (temp dirs in /tmp only); bash 3.2/4 and DH compatible; keep the diff to build-site.sh surgical (stage bodies unchanged apart from calling the wrapper).
