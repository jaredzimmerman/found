# T10: VPS watchdog
Tier: sonnet · Reviewer: opus · Deps: T01 (needs only contract C5/C11)

## Brief
Goal: an out-of-band watchdog on the Hermes VPS that tells Jared when the whattodo72 feed is stale or the build is failing, and when it recovers.
Contract: PLAN.md C5 (status.json fields) and C11 (conditions, cooldown, channel D1).
Files: `ops/watchdog.py` (python3 stdlib only), `ops/install-watchdog.sh`, `tests/watchdog.test.py`, do NOT edit `tests/run-all.sh`: it auto-discovers `tests/*.test.mjs|sh|py`.
Rules:
- Inputs: status via `ssh dh-backup cat ~/whattodo72.com/test/logs/status.json` (run on the VPS); public feed via `https://whattodo72.com/events.json` (urllib, 20 s timeout). Overrides for tests: `--status-file`, `--feed-file`, `--state-file`, `--now ISO`, `--dry-run` (print messages, send nothing, do not write state).
- Conditions, dedupe and recovery exactly as C11: stale >14 h; last outcome rejected/fatal once per run_id; required source zero_streak >= 3; public generatedAt >14 h old or unreadable JSON; DH unreachable (ssh failure) reported as its own condition; same condition at most every 6 h; one recovery message when everything is clear again. State in `/root/.local/state/whattodo72-watchdog.json` (created 0600).
- Delivery: `hermes send` (read `hermes send --help` on the VPS: `ssh hermes 'hermes send --help'`); message = a one-line subject + 3-6 plain lines (what is wrong, since when, last good count, what is still being served). Plain wording, no jargon, no emoji. If `hermes send` fails, log to stderr and exit 2 WITHOUT updating the cooldown state so it retries.
- `ops/install-watchdog.sh`: idempotent; backs up the crontab to `/root/backups/crontab-pre-whattodo72-watchdog-<ts>`; adds `*/30 * * * * flock -n /run/whattodo72-watchdog.lock timeout 120 python3 /root/projects/whattodo72-site/ops/watchdog.py >> /root/.local/state/whattodo72-watchdog.log 2>&1`; supports `--check` (print whether installed) and `--remove`. Do NOT install it in this task and do NOT send any real message (T12 does both).
Acceptance: `python3 tests/watchdog.test.py` exits 0 (>= 20 checks over canned status/feed files incl. cooldown, dedupe by run_id, recovery, unreachable) and `bash tests/run-all.sh` exits 0.
Constraints: python 3.9+ compatible; no third-party packages; never log secrets; ssh with `-o BatchMode=yes -o ConnectTimeout=10`.

## Review
Round 1 (opus) verdict: **changes**

Acceptance re-run: `python3 tests/watchdog.test.py` -> `55 passed, 0 failed` (exit 0); `bash tests/run-all.sh` -> `ALL PASS: 31 checks/files` (exit 0). Python 3.9 syntax check (ast feature_version=(3,9)) passes; stdlib only; ssh uses `-o BatchMode=yes -o ConnectTimeout=10`; state file created 0600 via mkstemp+fchmod; dry-run sends nothing and writes no state; failed send exits 2 without touching cooldown; run-all.sh untouched.

Blocking:
1. ops/watchdog.py:314-316 (with 145-157): cooldown is lost whenever a condition drops out of `present`, so the same condition re-alerts far more often than every 6 h (C11 breach). Worst case: one ssh blip makes every DreamHost-derived condition (stale, build_failed, source_zero:*) look "cleared" because it could not be evaluated, the key and its `last_sent` are deleted, and on the next good ssh it is "new" and is sent again. Reproduced with canned files (stale status, ssh alternating ok/unreachable every 30 min): stale alert at 20:00, 21:00, 22:00 and "cannot reach" at 20:30, 21:30 = 5 messages in 2 h. The same happens to any flapping condition (e.g. a transient feed fetch error: alert, "back to normal", alert again within minutes). Fix: when status is unreachable/unreadable, carry forward the DH-derived active keys untouched instead of clearing them; and keep `last_sent` for cleared keys (e.g. a separate map pruned after 6 h) so a condition that comes back within 6 h is not resent. Add tests for both.

Non-blocking:
2. ops/watchdog.py:325-326: when the recovery send fails, cleared keys are re-added with `last_sent=now`; if a condition then reappears it is suppressed for 6 h although it was never reported in that episode. Fold into the fix for 1.
3. ops/install-watchdog.sh:29: `--remove` when the watchdog line is the only crontab entry: `grep -vF` outputs nothing and exits 1, so with `pipefail` the script exits 1 after it has already emptied the crontab, and never prints "removed". Reproduced (exit=1, tab empty). Use `{ grep -vF "$MARK" || true; }`.
4. nit: ops/watchdog.py:319-320: the recovery message has 2 body lines; the brief asks for 3-6.
5. nit: ops/watchdog.py:165: "builds should land every 6 hours" - prod cron is 00:12, 07:12, 13:12, 19:12 (gaps of 5-7 h); "about four times a day" is accurate.
6. nit: commit 427bbda ("ladder: T10") also swept in T07's build/validate-feed.mjs, tests/fixtures/feed-good.json, tests/validate.test.mjs and tests/replay/record-preload.mjs from the shared tree (parallel-task checkpoint, not a T10 code defect).
